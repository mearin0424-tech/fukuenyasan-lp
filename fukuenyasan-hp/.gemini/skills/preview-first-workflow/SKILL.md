# Preview-First Workflow Skill

ユーザーからWebサイトやアプリケーションのコード修正指示を受けた際、**直接ファイルを更新せず、まずプレビュー（画面や変更差分）を提示し、ユーザーの「OK」を確認してから実際のソースコードに反映し、Gitへコミット＆プッシュする**ための標準ワークフローです。

---

## ワークフロー手順

### Step 1: 修正指示の解析と準備
1. ユーザーからの修正指示（デザイン変更、文章変更、機能追加など）を受け取ります。
2. 変更対象となるファイル・コンポーネントを特定します。
3. 必要に応じて、プレビュー確認用の静的Webサーバー（例: `http-server`, `python -m http.server` など）を起動します。

### Step 2: 修正案（プレビュー）の作成と提示
1. 直接本番ファイルを更新せず、一時ファイル（例: `.preview` サフィックスやスクラッチ領域）を作成するか、変更予定のコード差分（Diff）を整理します。
2. プレビュー用サーバーがある場合は、該当URL（例: `http://localhost:8124/`）で修正結果が確認できる状態にします。
3. ユーザーに対して以下を明確に提示します：
   - **変更内容の要約**（どこをどのように変更したか）
   - **コード変更差分（Diff / スニペット）** または **確認用URL / プレビュー手順**
   - **確認依頼メッセージ**（例：「こちらの変更案で問題なければ『OK』とお知らせください。本番ファイルへ反映してGitへPushいたします。」）

### Step 3: ユーザーの確認待ちとイテレーション
- **ユーザーが修正・再調整を希望した場合**:
  - 指摘事項を反映して修正案を再作成し、再度Step 2のプレビュー提示を行います。
- **ユーザーがキャンセルを希望した場合**:
  - 作業を中断し、変更は破棄します。

### Step 4: 本番ソースコードへの反映（承認時）
1. ユーザーから「OK」「承認」「反映して」といった明確な同意を得たら、`replace_file_content` や `write_to_file` を使用して、実際のソースコードへ変更を反映します。
2. 一時ファイルやスクラッチファイルをクリーンアップします。

### Step 5: Gitへのコミット & プッシュ（自動完了処理）
1. 変更したファイルをステージングします: `git add <変更ファイル>`
2. 変更内容に合わせた分かりやすいコミットメッセージでコミットします: `git commit -m "..."`
3. リモートリポジトリへ変更を送信します: `git push`
4. ユーザーへ最終的な完了報告を行い、作業を完了します。

---

## エージェントへの注意事項
- **勝手に本番ファイルを上書きしない**: ユーザーからの「OK」が出るまでは本番ソースコードを上書き変更してはいけません。
- **承認なしでPushしない**: ユーザーの「OK」を確認してから、コード反映とGit Pushを行ってください。
- **わかりやすい視覚的説明**: プレビュー提示時は、何がどう変わるのかを非エンジニアにも直感的に伝わる言葉で記述してください。
